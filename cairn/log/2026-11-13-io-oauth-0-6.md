# Move to io-oauth 0.6

Cargo.toml requires io-oauth 0.6, released on 2026-11-13 on io-http 0.7; Cargo.lock moves io-oauth 0.5.2 to 0.6.0 and io-http 0.6.0 to 0.7.0, one version of each, and nothing else. pimalaya-cli, pimalaya-config and pimalaya-stream keep their requirements.

- The redirect listener takes the expected state. `auth get` passes the state it generated, `auth listen` its `--state` (none when omitted), the MCP server the state of its flow. A request that does not echo it, goes to another path, is not a `GET` or never ends its request line is answered `404 Not Found` and the wait goes on, where any connection ended it before.
- The MCP server stopped a replaced flow's listener with an empty connection, which the new listener skips: the thread and its port stayed, and a configured port could not be bound by the next `auth_get` (`Address already in use`). `McpListener::stop` (src/mcp.rs) sends the one request the listener takes, a refusal echoing the flow's state, then joins the thread when it answered within 2 seconds. The flow being replaced first, nobody reads that refusal.
- `Oauth20AuthParams::validate` takes the expected issuer (RFC 9207). Ortie passes `None` for every account: the configuration names no issuer and nothing reads server metadata since the wizard left. An `issuer` key on the account is what the check waits for, a decision left to the maintainer.
- The device grant uses `lifetime()` (one hour at most) and `poll_interval()` (1 to 60 seconds). The command line polls through io-oauth, bounded by the release itself; the MCP server has its own loop, which added the raw `expires_in` to an `Instant` (a panic on a large value) and polled without pause on an interval of 0. Its next poll never outlasts the deadline. The device response `auth get` prints carries the bounded values.
- `expires_in` of a token is an `Option<u64>`: `TokenInspectOutput::expires_in` follows (its schema `format` moves from `uint` to `uint64`, as the device response's `expiresIn` and `interval`), and the expiry sums saturate.
- `--pkce` goes through the validating constructor, which refuses a verifier outside 43 to 128 unreserved characters and names a length or a byte, never the verifier. `--state` and the generated state go through `Oauth20State::try_from`.
- A non-success status without an OAuth error body ends in `Status(u16)`, which the commands print as they print every error ("Unexpected client credentials status 503").
- Ortie built no request body and logged no request params, so the removed `Display` touches nothing. Client authentication stays HTTP Basic from `client-secret`, form-encoded by the library first.

Tests: tests/auth_listen.rs sends a forged redirect before the real one in `a_handed_off_flow_is_listened_for_and_stored`; tests/mcp.rs gains `a_request_not_echoing_the_state_does_not_end_the_flow`, `a_new_flow_binds_the_configured_port_again` and `a_device_flow_bounds_the_lifetime_and_the_interval_of_the_server`; tests/device_grant.rs `auth_get_reports_the_lifetime_and_the_interval_bounded`; tests/client_credentials.rs `an_error_status_without_an_oauth_body_is_reported`. Each of the first five failed with the adoption taken back out of src (no state passed, an empty stop request, the raw lifetime and interval). `pkce_code_verifier_parser_error_omits_verifier_body` pinned the former message and now checks both refusals.

Capabilities moved: auth (cairn/spec/auth.md: "Only the redirect of the flow ends the wait", "The issuer is not compared" and "A bare error status is named" added, "Manual resume fallback", "Device grant runs"), mcp (cairn/spec/mcp.md: "The flow lives in the server"), token (cairn/spec/token.md: "Storage round-trip").
